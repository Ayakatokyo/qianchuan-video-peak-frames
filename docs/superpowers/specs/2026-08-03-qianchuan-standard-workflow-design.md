# 千川素材分析标准工作流设计

## 背景

技能的业务目标是：用户提供分析周期、Top 素材数量和广告主 ID 后，获得一份可追溯的千川短视频素材分析报告。当前实现已经具备资产表选材、波次 RPA、峰值帧处理、AI 二次分析和报告渲染能力，但把正常运行、单素材调试、旧批次兼容和故障修复暴露在同一技能流程中。主入口因此同时管理预检、恢复、校验、并发调度和多种历史产物。

本设计保留已有的可靠性机制，但将它们从技能的业务主流程中下沉为内部实现细节。

## 目标与非目标

目标：

- 为常规业务运行提供唯一标准入口，只接受周期、目标 Top N 和广告主 ID 三个业务条件。
- 将执行过程收敛为“选材 -> 诊断与证据生成 -> AI 分析与报告”三个用户可理解的阶段。
- 保留候选池、波次请求、失败补位、下载重试、串行补偿、产物校验和审计清单，确保目标数量按最终可分析素材数计算。
- 为排障保留独立工具和稳定产物，但不要求业务用户理解或手动编排它们。
- 保持既有的日期、广告主、峰值帧、事实证据和 AI 输出契约。

非目标：

- 不改变资产表排名口径、RPA 连接器协议或点击峰值识别算法。
- 不删除仍被正式批次或恢复流程依赖的产物格式。
- 不让模型直接绕过事实包生成 HTML，也不将执行故障写入业务结论。

## 标准入口

新增 `scripts/run_standard_analysis.py` 作为面向技能执行的标准编排入口。它接收：

- `startDate` 与 `endDate`：由自然语言周期换算得到的闭区间。
- `topN`：最终成功完成后处理、可进入报告的素材数量。
- `advertiserId`：资产表筛选条件，并与 RPA 店铺映射校验。

RPA 店铺、认证信息、并发度、超时和输出根目录为受控环境配置或安全默认值，不再作为标准技能流程的业务决策。入口输出一个运行目录，其中只有以下内容属于业务交付：

- `final-report/`：完整 HTML 报告及其 JPEG 资产。
- `run-summary.json`：输入条件、最终成功素材数量、报告路径和可读的失败摘要。

其余 `top_materials.json`、诊断 records、帧文件和 manifest 是内部审计产物，保留但不在正常操作说明中展开。

## 内部数据流

```text
用户三个条件
  -> 周期规范化与资产表筛选
  -> 有序候选素材池
  -> 波次 RPA 诊断
  -> records 持久化、视频下载、峰值帧提取
  -> 失败重试、串行补偿与按排名补位
  -> 最终可分析素材集合
  -> 事实包 + AI 结构化结论
  -> 校验后的 HTML 报告与运行摘要
```

第二阶段的完成条件是 `postprocessSucceededCount >= topN`，不是 RPA 已提交或已选中数量。候选池默认大于 Top N；仅在前序候选无法获得合格业务事实或无法生成足够视觉证据时，才按排名提交后续波次。成功素材必须保留零秒帧；存在局部峰值时至少保留一张峰值帧。预期帧缺失应在对应素材的 AI 深度分析中披露。

`top_materials_rpa_ready.json` 是后续事实包和报告的唯一素材清单。事实包和报告仍各自校验素材覆盖、证据引用与已复制的帧资产，避免候选池或不完整素材误进入业务结论。

## 模块边界

标准入口只负责参数规范化、阶段调用、面向用户的状态汇总和最终退出码。它不直接处理 RPA 响应、下载视频或构造报告。

内部模块分为四类：

- `selection`：资产表查询、跨日期聚合、候选排序和选材产物。
- `diagnosis_batch`：唯一的标准波次调度器，负责 RPA、records 持久化、后处理、补位、manifest 和最终校验。
- `frame_processing`：从已归一化 records 下载视频、选择峰值、抽帧并生成单素材摘要。
- `reporting`：构造紧凑事实包、接收模型结论、校验结论并渲染最终报告。

现有 `extract_peak_frames.py` 应演变为薄 CLI 适配器或被替代；不得继续同时承载标准批次、legacy 批次、预检、恢复和单素材调试的分支。`rpa_batch_runner.py` 中的 streaming 调度器是标准批处理内核；legacy batch 与预检调度器在迁移后不再由标准入口引用。

## 可靠性与故障处理

正常入口自动执行产物校验，不要求用户执行 `--verify`。RPA 超时、迟到 CSV/records 回收、下载有限重试、已落盘 records 的串行补偿、候选补位和运行锁均保留在 `diagnosis_batch` 内部。

运行中断或内部状态不一致时，标准入口返回失败并在 `run-summary.json` 中指出运行目录与恢复建议。`repair_manifest.py`、旧 `--resume`、单素材 RPA 和本地 CSV 模式保留为运维/开发工具，不出现在标准技能工作流；它们在无正式使用者后才删除。

## 迁移步骤

1. 先修正当前基线的契约漂移：部分峰值帧缺失但满足最小视觉证据时可以交付，测试与提示词必须一致。
2. 提取标准批次内核，确保只有 streaming 波次调度器处理新 Top-N 批次。
3. 增加标准入口和 `run-summary.json`，由入口内部完成选材、批处理、事实包、模型交接与报告校验。
4. 将 `SKILL.md` 重写为三阶段说明，只保留标准入口和必要的 AI 结论生成动作；运维工具移入单独的故障排查文档。
5. 在测试、真实批次和调用记录确认无使用后，删除或归档 legacy/preflight 公开分支与重复帮助文本。

迁移期间保留现有 manifest schema 和 `top_materials_rpa_ready.json`，使未完成批次仍可恢复，报告模块不必同步重写。

## 验证

- 标准入口只暴露三个业务输入，并能以同一日期区间和广告主 ID 生成候选池。
- RPA 成功但后处理失败时，入口重用 records 执行有限重试、串行补偿和按排名补位，且不重复有效 RPA 请求。
- 成功数量不足时运行失败但保留可审计产物；成功时只把最终 Top N 写入 ready 素材清单和报告。
- AI 结论必须引用事实包证据、覆盖所有最终素材和已生成帧，最终报告只接受通过校验的结论。
- 标准入口、恢复工具和单素材调试各有独立测试；标准流程测试不得依赖 legacy 或预检分支。

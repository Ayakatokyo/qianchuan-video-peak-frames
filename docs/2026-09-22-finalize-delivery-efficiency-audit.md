## 证据与结论

1. 最新运行的采集/后处理约 102 分钟，AI 分析约 20 分钟，报告阶段约 44 分钟；其中报告阶段约 42 分钟消耗在高内存重试和归档失败上。
2. Bash 日志中有 99 次调用，存在多轮状态读取、短等待和进程探查。这些调用并不加速后台任务，反而增加了控制面开销和失联后的误判概率。
3. 一次用 `setsid` 脱离会话的长进程在控制通道结束后仍持续运行并完成，证明“长任务与单次 Bash 会话解耦”是更稳定的执行方式。
4. HTML 报告本身可成功生成，默认 ZIP 打包峰值内存接近 960 MB 并被系统终止；历史压缩包约 125–333 MB，最新报告目录约 1.3 GB。ZIP 不应继续作为默认交付前置条件。
5. 仓库有 36 个 Python 文件，但直接 CLI 入口只有 5 个；静态引用检查未发现无引用模块。慢的主因不是“脚本文件多”，而是默认路径做了不必要的工作簿、压缩、大对象复制、重复读文件和控制面轮询。因此本次不做高风险的模块合并。
6. `running/report` 本来被 `finalize` 识别为可恢复，但内部校验只接受 `analysis_pending`，导致中断后重试必然失败。

## 已实施优化

- `finalize` 默认只生成 `final-report/` 和 HTML，不生成 XLSX 或 ZIP；工作簿与归档分别改为 `--include-workbook` 和 `--archive` 显式开关。
- 报告视频不做第二次 FFmpeg；优先使用硬链接复用已下载 MP4，不支持时才原子拷贝。
- 默认路径不再检查 OpenPyXL/Pillow；只在要求工作簿时启用该依赖门禁。
- 修复 `running/report` 的 finalize 断点续跑，并保留输入哈希不变时的阶段复用。
- v1 报告路径不再深拷贝整个 `displayFacts`；复用已读取的 presentation；HTML JSON 转义由多次整串替换改为单次 `translate`。
- 源视频删除只允许在显式生成并校验归档后进行，防止精简默认交付路径后破坏可恢复性。
- 技能与运维手册改为长任务首次启动即脱离 Bash 会话，后续以 `status.nextAction` 驱动，不再默认组合多轮短查询。
